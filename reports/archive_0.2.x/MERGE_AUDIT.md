# AMDE 0.2.1 — Merge and hardening audit

**Audit date:** 2026-10-29  
**Input:** the six-entry user-provided `full.zip` (source archive SHA-256 `6b57eeb46aa98163945f00dcb73b4bba505514eb84d3463d027a3d4e1c5c5215` in `manifests/SOURCE_MANIFEST.json`) and the partially merged release repository `AMDE_Integrated_24x7_Release.zip` (`a3d5ad71b6cf710dab7d13829bdb19418182ecc6368eb20b3034468f3d54df89`).  
**Scope:** merge decisions, regression fixes, reproducibility, resource control, virtual/network filesystem durability, long-run operations, and limits of the evidence.

## Executive decision

The final project is based on the most complete runnable implementation among the six inputs (the archive member labelled `deepflash.zip`, SHA-256 `490bfcfb0a715e020f009f764727693105b118a04520b4b24c441af5fea6c3c5`); this is an artifact label, not an inference about which AI model authored the code. It combines that architecture's ledger, checkpoint/recovery, candidate schema/DSL, evaluator isolation, baseline and search components with a controlled-experiment runner adapted from the `clau.zip` research design, passive stagnation diagnostics and resource/telemetry improvements informed by `antigrav.zip`, and additional durability and boundary hardening verified in this session. Unique ideas were reimplemented where the original code could not safely be transplanted. Redundant and failing code was deliberately not bulk-copied.

The resulting project is **a hardened research prototype for bounded synthetic/tabular tasks**, not a demonstrated system that invents arbitrary new learning algorithms, solves ARC, or becomes better without limit while running 24/7.

## Important fixes and hardening

1. **Search reproducibility bug fixed (`src/amde/util.py`, `src/amde/orchestrator.py`, `src/amde/config.py`).** The original search RNG was seeded with `(configured_seed, run_id, "search")`. This made identical nominal seeds/configurations diverge merely because output-directory names differed, weakening paired comparisons. The RNG now derives from the experiment seed only via `search_seed_for()`; use distinct experiment seeds for independent replicates. Unit and end-to-end integration regression tests (`test_search_seed_depends_on_experiment_seed_not_run_id`, `test_search_reproducibility_is_independent_of_run_id_and_guards_protocol_hash`) verify that distinct run IDs produce the exact same candidate hashes and scores, and the rule is versioned into the protocol hash as `amde-search-rng-v2-seed-only` so old caches/checkpoints are not silently treated as equivalent.
2. **Virtual / network filesystem `fsync` and SQLite WAL resilience (`src/amde/util.py`, `src/amde/runtime/lock.py`, `src/amde/storage/ledger.py`).** Running `smoke` or `once` directly on virtual/FUSE-backed filesystems that reject `os.fsync` with `OSError: [Errno 95] Operation not supported` previously caused `SingleInstanceLock.acquire()`, `atomic_write_bytes()`, and SQLite `WAL` commits to fail. Added `safe_fsync()` and directory `fsync` capability probing in `Ledger`: when `fsync` is supported (standard local NTFS/ext4), `journal_mode=WAL` and `synchronous=NORMAL` are used; when `fsync` is unsupported by the mount, `Ledger` falls back cleanly to `journal_mode=MEMORY` and `synchronous=OFF` and guards `ROLLBACK` with `in_transaction`.
3. **Linux `/proc/meminfo` fallback & enriched heartbeat telemetry (`src/amde/runtime/resources.py`, `src/amde/orchestrator.py`).** When optional `psutil` is not installed on Linux, `detect_hardware()` and `ResourceSampler.snapshot()` previously reported `0 MB` RAM; they now parse `/proc/meminfo` (`memory_source="proc-meminfo"`) while preserving Windows `GlobalMemoryStatusEx` (`memory_source="windows-api"`) and `psutil` (`memory_source="psutil"`). `heartbeat.json` now records `device_effective`, `gpu_effective`, `cpu_workers`, `generation`, `trials`, and the latest resource snapshot.
4. **Task-family holdout support (`src/amde/config.py`, `src/amde/orchestrator.py`).** Added `Config.dev_task_specs()` and `Config.challenge_task_specs()` supporting `"holdout_only": true` on task specifications so held-out task families are never evaluated during quick screening, baseline selection, or dev confirmation, and cannot be added to `quick_task_ids`.
5. **Optional tensor trainer (`src/amde/models/torch_trainer.py`).** The PyTorch implementation is optional and only selected after an actual CUDA tensor smoke test and resource checks. CPU reference remains the default/fallback. Numerical parity was checked for linear/MLP/DSL update-rule paths and supported optimizers on CPU. CUDA execution is **not verified in this environment**.
6. **Device-specific protocol/cache (`src/amde/config.py`, `src/amde/evaluation/evaluator.py`).** The effective training device is included in the evaluation/cache protocol so CPU results are not reused as CUDA outcomes or vice versa.
7. **Memory reserve & worker bounds (`src/amde/config.py`).** RAM reserve scales with total memory (`max_reserve_fraction`) while preserving the safety floor (`minimum_reserve_mb`); worker concurrency is bounded by available cores/memory. GPU concurrency is one by default on the small-memory target class.
8. **Long-run log growth & launcher symmetry (`src/amde/orchestrator.py`, `scripts/watchdog_24x7.ps1`, `scripts/report.ps1`).** Engine logs use rotating file handlers; watchdog attempt logs have bounded retention (40 newest files); added `scripts/report.ps1` for PowerShell symmetry with `scripts/report.bat`. Checkpoints, ledger and source reports are never deleted by the watchdog.
9. **Passive stagnation diagnostics (`src/amde/search/stagnation.py`, `src/amde/orchestrator.py`).** Reports plateau status, invalid rate, phenotype diversity and recommendations in both the generation ledger and generated Markdown run reports (`## Search Diagnostics & Stagnation`) without silently changing metrics, search policy or the validation split.
10. **Control experiment (`scripts/control_experiment.py`).** Uses common task/protocol hashes and matched generation/proposal budgets to compare `portfolio`, `random_only` and `hpo_A`. Reports are explicitly labelled development-only, not generalization evidence.

## Not verified / not claimed

- The current verification environment is a Linux x86_64 container (Python 3.11.2, no GPU, no Windows PowerShell); it is not the user's Windows PC.
- PowerShell `.ps1` and batch `.bat` launchers were reviewed for syntax and path quoting (`REVIEWED ONLY`), **not runtime-tested on Windows** in this session.
- CUDA training is **not runtime-tested on GPU hardware** (`BLOCKED` in this environment due to no physical GPU). The project must be checked with `scripts\doctor.bat` on the actual PC before enabling unattended work.
- No local ARC task JSON is included. Doctor reports ARC `BLOCKED` (0 local tasks); the current engine's ARC adapter is read-only/baseline-only, not an ARC-learning implementation.
- The discovery space remains intentionally bounded to small tabular ML candidates/allowed DSL. It does not write arbitrary code and has not demonstrated discovering a novel optimizer or an algorithm superior to traditional methods on a held-out, multi-seed benchmark.
- A smoke score, passing tests, or uninterrupted runtime does not imply research validity or guaranteed long-term progress.

## Recommended deployment gate

On the Windows PC: run `scripts\setup_venv.bat`, run `scripts\doctor.bat`, run a bounded `scripts\run_smoke.bat`, check `scripts\status.bat` and `scripts\report.bat`, verify a graceful stop (`scripts\stop.bat`) and resume, and inspect CPU/GPU temperatures and free disk. Only then start `scripts\watchdog_24x7.bat`. If `doctor` reports CPU, regard it as CPU mode; do not claim GPU acceleration until a real CUDA tensor-training run and CPU/tensor parity check pass on that machine.
